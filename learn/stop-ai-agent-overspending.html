How to stop an AI agent from overspending

A rule written in an agent's prompt is a suggestion. One clever message can argue the agent out of it. A real spending limit lives outside the agent and is checked at the moment of paying.

Why "tell the agent not to overspend" fails

An AI agent decides what to do by reading text. Text can be changed by anyone who can get words in front of the agent: an email it reads, a web page it opens, a message from a supplier, a document with hidden instructions. If the spending rule is part of that text, it can be overridden by the same route. Security people call this prompt injection. The fix is not a better prompt. The fix is to put the limit somewhere the agent cannot edit.

Five controls that hold

1. A limit that is signed by a person and checked outside the agent

The permission says who may be paid, how much per payment, for what purpose and until when. It is signed, so it cannot be forged or edited. A separate service checks it on every payment. The agent can ask for anything; the service only says yes inside the signed limit. No AI model should make this decision, because a model can be talked round and a signed number cannot.

2. Three kinds of limit, not one

LimitWhat it stops
Per paymentOne big mistake or one big fraud.
Total over the life of the permissionDeath by a thousand small payments.
Speed (for example, no more than five an hour)A looping or hijacked agent draining money quickly.

All three must be counted exactly, including when several servers handle payments at once. Round amounts up, never down, so a fraction cannot slip under a limit.

3. A person for the big ones

Above an amount you choose, a named person must approve that exact payment. For very large amounts, two different people. The agent must never be able to approve its own payment. Approval of "the agent" in general is weaker than approval of one amount to one recipient.

4. A kill switch that works at once

You need to be able to cancel a permission in one click, including a permission that was passed on to another agent. A cancelled permission must fail on the very next request, not at the next login.

5. The agent never holds the raw key

If the agent holds an API key that can spend, anyone who steals or tricks that key can spend. Give the agent a limited key that can only ask to pay, and keep the signing key somewhere the agent cannot read. Then a stolen key is held small by the limits above.

A quick checklist for any tool you evaluate

  • Is the limit enforced outside the agent, at the payment, and does it fail closed if the checker is down?
  • Does it count totals and speed, or only the size of one payment?
  • Is the decision made by an AI model, or by signatures and exact numbers?
  • Can a large payment require a named human, and can the agent approve its own?
  • Can you cancel a permission and see the next payment refused?
  • Is there a record nobody can quietly change?

Questions people ask

Can I just put a spending limit in the system prompt?

No. A prompt rule can be overridden by any text the agent reads. Put the limit in a signed permission that a separate service checks on every payment.

What is a good spending limit for an AI agent?

Start small and widen it. Set a per-payment limit, a total cap, a speed limit and a human approval threshold. Review the refusals each week and adjust.

Should a human approve every agent payment?

No. That removes the benefit. Let the agent prepare payments inside strict limits and require a named person only above a threshold you choose.

What happens if the agent's key is stolen?

If the key can only ask to pay inside a signed permission, the thief is held to the same limits. A cancelled permission stops working immediately.
