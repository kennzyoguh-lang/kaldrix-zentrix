x402 spending limits for AI agents

x402 lets a web server ask for payment and an agent pay it. The protocol does not say how much an agent may spend in total, whom it may pay, or when a person must approve. That has to be added.

How x402 works in one minute

  1. The agent requests a web resource.
  2. The server answers 402 Payment Required and describes what it wants (the amount, the token, who to pay, which network) in a PAYMENT-REQUIRED header.
  3. The agent signs a payment and tries again with a PAYMENT-SIGNATURE header.
  4. The server verifies the payment, often through a facilitator, and returns the resource.

It is fast and works without accounts. The risk is the same speed: an agent that loops, or is told to buy from a malicious server, can sign many payments quickly.

Where the limit has to sit

The only safe place is between step 2 and step 3: after the server has said what it wants, before the agent signs. If the limit sits after signing it is too late, and if it sits in the prompt it can be argued away. A guard here does these things in order:

  1. Reads the request and refuses anything malformed.
  2. Checks a policy: only listed tokens, only listed recipients, only listed websites; a limit per payment, a total cap, a speed limit; a maximum time the payment may stay valid; a person approves above an amount.
  3. Signs only if the policy allowed it.
  4. Checks what was signed against what was approved (same amount, recipient, token, network).
  5. Sends, and gives the reserved amount back if the server still says 402.

Two details people get wrong: amounts must be exact whole units with no floating point, and rounded up, so a fraction cannot slip under a limit; and if the connection drops after sending, the amount must stay counted because the payment may have gone through.

A small open-to-read example

const guard = createGuard({
  allowedAssets: [{ network: "eip155:8453", asset: "0xUSDC_CONTRACT", symbol: "USDC", decimals: 6 }],
  allowedRecipients: ["0xSupplierWallet"],
  allowedHosts: ["api.supplier.com"],
  maxPerPaymentUsd: 1,
  maxTotalUsd: 20,
  speed: { windowMs: 60_000, maxUsd: 3 },
  requireApprovalAboveUsd: 0.5,
});
const pay = guardedFetch(fetch, guard, mySigner, { approve: askAPerson });

This is from our public x402 guard. It is a first version, written against the x402 specification version 2, with tests for every refusal. It is a policy check, not a vault: if anything else can reach the wallet key directly, it can sign without asking the guard.

When a signed permission decides instead of a settings file

A local settings object is easy but the agent's own code can change it. A stronger setup asks Kaldrix before the agent signs: does a signed permission a person gave this agent allow this exact payment? Kaldrix checks the amount, supplier and purpose, counts the spend against the total cap, asks a person to approve a large payment, writes an audit record and returns a signed proof. If Kaldrix says no, or cannot be reached, nothing is signed. In the test service the payment itself goes to a pretend bank; Kaldrix does not watch the blockchain settle.

A facilitator that checks authorization

x402 lets a server ask a facilitator to verify and settle a payment. Zentrix runs one in the test service that adds the check x402 does not make: a payment is valid only if it carries a Kaldrix permission and the agent's own proof for that exact payment. A well-formed payment with no permission, to an unregistered address, over the limit or with a stretched amount is refused before anything is settled. It uses a made-up token on a test network: there is no blockchain, and the wallet signature is not checked.

Questions people ask

Does x402 limit how much an agent can spend?

No. The protocol describes how to ask for and make a payment. Limits have to be added by the client that signs, or by a service it asks.

Where should the spending limit go in an x402 flow?

Between the server's 402 answer and the agent's signature, so nothing is signed that the policy did not allow.

Why round amounts up when checking limits?

So a fraction of a unit cannot slip under a limit through rounding.
